01 Problem

An amateur actor learning a part usually rehearses alone, from a paper script, with nobody to read the other characters' lines. The app began as the missing scene partner. It reads everyone else's lines aloud and waits for you, and every feature is judged against one question: would a good scene partner do this?

Then a director saw it and asked for the whole company. A single-user offline app had to become a multi-user production tool, without throwing away the core that already worked.

02 How it was built

Every version follows the same planning ritual before any code is written: requirements → data model → a pass/fail spike on the riskiest assumption → architecture and ADRs → a "future" list with explicit triggers → a development plan with a pre-committed cut list. Each version then gets its own branch, its own docs folder and an on-device gate before it merges.

That discipline is what let the app absorb a pivot. It shipped 24 versions, eight of them in eight days, while the domain code stayed free of framework imports.

03 Architecture

Ports and adapters. The rehearsal engine, the line aligner and the casting, calendar and ticket rules live in a pure Dart core that imports nothing but its own interfaces. Speech, audio, storage, sign-in and push are adapters behind 28 ports. The core's tests run on the host machine, with no simulator.

04 Key decisions

ADR-055

Locate the speaker, don't transcribe them

Context
Speech-to-text output is noisy, especially for verse and for a theatre company's own adaptation of the text. But the app already knows exactly which line the actor is meant to be saying.
Decision
Use recognition only to find where in the known line the speaker is. A pure aligner in the domain does the matching, and the speech port is opt-in.
Trade-off
It can't catch ad-libs. In return it's far more robust, testable without a device, and degrades to plain recording.

ADR-058 / 059

Sell tickets on the web, run the door in the app

Context
The company wanted to sell show tickets. App-store rules treat real-world event tickets differently from digital goods.
Decision
Buyers purchase on a public web page through Stripe Checkout, and the app holds only the organiser's box office: scanning and admission.
Trade-off
A second surface to maintain, the web app, in exchange for a clean payment flow outside in-app purchase.

ADR-062

The server decides who gets in

Context
A ticket QR code can be copied, and two door phones can scan the same ticket at the same moment.
Decision
The QR holds a 32-byte opaque token and nothing else. Admission is a server-side function that locks the row and admits each ticket exactly once. The client only renders the verdict, and the same token powers the wallet pass.
Trade-off
The door needs a connection. Correctness at the door is non-negotiable.

ADR-063

Retiring a founding principle

Context
The app was founded on "don't grade the actor". It existed to help, not to judge. An adult cast later asked for word-for-word checks.
Decision
Reverse it explicitly in a new ADR: add a line verdict biased toward false negatives, framed as progress rather than a score, and scoped to production use.
Trade-off
A principle is gone. Writing down why keeps it from coming back by accident.

05 Hard problems

A font that silently wasn't there

The scripts include polytonic Greek. A spike on day two found that the hosted copy of the chosen typeface quietly fell back to a different font. Only a deliberate side-by-side test, with the font on and with it off, caught it. Downloading the font directly fixed it, and table-level checks on the font file then unlocked real small caps.

Silence detection that never fired

The voice-activity detector worked in offline tests and never triggered on a phone. The audio library reported levels on a 0–120 scale, not the dBFS the threshold assumed, and the level stream was null until the recorder opened. I recalibrated with an on-screen meter. The lesson went into the journal: offline spikes can't validate adapter integration.

A metric that scored a correct line zero

The first line-accuracy measure, a longest-common-subsequence score, gave a correctly spoken line 0.00 because of a single mis-heard word. Reusing the aligner's own walk through the line gave 0.57 on the same input, and a threshold that matches what a listener hears.

06 Outcome & what I'd do differently

Aristophanes is in use by a 12-person adult cast, distributed through TestFlight on iOS and Firebase App Distribution on Android, with ticketing running in Stripe test mode. The repo is private, and I'm happy to do a code walkthrough.

  • Never skip the device gate. A visual rework merged before its on-device check looked fine in screenshots and failed in actors' hands. It took a follow-up version to fix.
  • Watch the user, don't help them. The first user test turned collaborative, and half the questions on the watch list went unanswered.
  • Keep the scaffolding tidy. Per-version branches are powerful, but stale branches and a duplicated version number cost real time. Archive as you go.
